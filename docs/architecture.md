# Architecture

## Design boundary

The Evidence Engine is the system of record for task state and structured evidence. The language model is a consumer of reports, not the authority that decides whether its own actions succeeded.

```text
Trusted host / operator configuration
            |
            v
     Task contract (fixed)
            |
            v
  Trusted execution adapters ------> External tools / processes
            |                               |
            | actual results                |
            v                               |
     Evidence Engine <----------------------+
            |
            v
  Deterministic verification
            |
            v
  Read-only report for the LLM / user
```

## Components in the first milestone

### Task contract

A task contains a title and one or more immutable success criteria. Each criterion specifies:
- evidence kind;
- payload field;
- operator (`exists`, `eq`, or `gte`);
- expected value, when applicable;
- optional source label;
- minimum number of matching observations.

Criteria must be supplied when the task is created. An LLM must not be allowed to rewrite the criteria after seeing the outcome.

### Evidence ledger

Evidence is structured JSON with a timestamp, kind, descriptive source label, and task identifier. Rows are appended to SQLite and linked using SHA-256 hashes.

The hash chain is intended to expose accidental or unsophisticated tampering. It is not a substitute for OS access controls, signed events, external checkpoints, or backups.

### Verification

Verification is deterministic and independent of the prose generated by the assistant:
- all criteria supported -> `supported`;
- any criterion contradicted -> `contradicted`;
- missing or invalid evidence -> `inconclusive`;
- broken evidence chain -> `invalid`.

Task finalization maps these outcomes to `passed`, `failed`, or `unknown`. No public method accepts a model-provided success flag.

## Trust boundaries

1. **Operator configuration is trusted.** Task criteria and adapter policies must be created by host-controlled code or an operator.
2. **Tool outputs are observations, not instructions.** Treat stdout, stderr, files, and external content as untrusted data.
3. **The model is not a source of execution truth.** Free-form claims from a language model must never be recorded as command exit codes, file hashes, test counts, or delivery receipts.
4. **Reports are derived.** The model may summarize a report but must not change its status or evidence.

## Planned extension points

- command adapter: allowlisted argv execution without a shell, timeouts, bounded output capture, exit code evidence;
- file adapter: allowlisted path inspection and SHA-256 snapshots;
- test-report adapter: structured pytest/JUnit parsing with exact test counts;
- Hermes bridge: read-only report retrieval, trusted host-side evidence submission;
- external checkpointing: signed or remote hash-chain anchors.

These are future milestones, not part of v0.1.
